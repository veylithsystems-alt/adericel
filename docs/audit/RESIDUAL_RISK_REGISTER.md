# Adericel Residual Risk Register

**Required by:** Contract v3.1 §38 (originally v3.0 §57)
**Opened:** 15 September 2026
**Owner of the register:** Veylith Systems (founder)

> §57: "Known limitations must never be hidden merely because they make the
> product look less mature."
>
> Every entry derives from the v3.0 Contract Gap Report and names what is
> actually true today. An entry leaves this register when the mitigation is
> implemented **and** evidenced, not when it is planned.

**Acceptance states:** `OPEN` (no mitigation yet) · `MITIGATING` (work in
progress) · `ACCEPTED` (understood, deliberately not fixed now, with a reason) ·
`CLOSED` (fixed and evidenced) · `WITHDRAWN` (the entry itself was wrong or has
been replaced by another, which it names).

**Identifiers are never reused.** They are also not contiguous: thirty-six
numbers below the highest are unused, and why each went unused is not recorded
anywhere in this repository and is not reconstructable. A gap therefore means
nothing was ever written under that number — it does not mean an entry is kept
somewhere else. `tests/unit/risk-register.test.ts` enforces what can be
enforced: no identifier appears twice, no entry refers to one that does not
exist, every entry's heading agrees with its `State` row, every closure cites
evidence, every live entry names an owner, and every repository path this file
cites is a path that exists.

| **Description**           | `ActionService.verify(actionId: string, observedValue: unknown)`. The second argument decides the verification outcome, and its type is `unknown` — any caller may pass anything. The one caller that exists, `POST /v1/organisations/:organisationId/actions/:id/verify`, does the right thing: it calls `collection.reobserve`, which re-runs the connector against the source and reads the claim that results. Nothing makes the next caller do the same.                                                                                                                                                                                                                                                                                                                                                                        |
| **Impact**                | **High, and exactly the class of thing this product exists to refuse.** A `CONFIRMED` verification writes a `verifications` row, which is evidence, which moves assurance state. A worker job, an n8n flow or a second endpoint that passed the executor's own report of success — or a literal `true` — would produce a verification indistinguishable from one earned by re-observing the source. Adericel would be asserting it had checked when it had only been told.                                                                                                                                                                                                                                                                                                                                                           |
| **Not yet exploited**     | No such caller exists today. This is a structural weakness, not a live breach: `grep` over `apps` and `packages` finds exactly one call site, and it re-observes. The defect is that correctness rests on every future caller remembering, which is the thing types are for.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| **Why nothing caught it** | Every test of the verification path goes through the route, which re-observes, so the path under test is the correct one. No test asks whether the _incorrect_ path is expressible — and until this entry, nothing stated that re-observation was part of the authoritative lifecycle, because the lifecycle was never reconciled (RR-080).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Mitigation**            | Make an unattested observation inexpressible. `reobserve` returns a branded value only the collection service can construct, `verify` requires one, and the brand is checked at run time as well as compile time because the API boundary deserialises JSON. A caller with no integration or no target passes the explicit "could not re-observe" value, which must force `UNVERIFIED` rather than being treated as a reading.                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Resolution**            | `packages/actions/src/reobservation.ts` owns a `unique symbol` brand it does not export, and mints a value carrying it only after performing the re-observation. There is deliberately no exported `attest()`: a constructor anybody could call would move the problem rather than solve it. The only ways to obtain a `ReObservation` are `reobserve`, which runs the integration, and `notObservable(reason)`, which can produce the absence of a reading but never a reading. `reobserve` was removed from `CollectionService` outright, so there is no longer a method returning a bare `unknown` that `verify` would accept.                                                                                                                                                                                                    |
| **Verified**              | Three layers, each proved by breaking it. The type stops the honest mistake. `assertReObservation` stops the cast and the JSON body, and runs before any state moves — a refused verification leaves the action in `VERIFYING` and writes no row, which is asserted rather than assumed. The database stops the forgery: migration `0034_verification_provenance.sql` makes `verifications.integration_run_id` a foreign key to `integration_runs`, so a fabricated run identifier fails at the insert, and a `CHECK` constraint means a row either names its run and when it was read, or names why no run was possible — never neither. `tests/security/verification-attestation.test.ts`, 15 tests, attacks the boundary at the service rather than through HTTP, because a route is not the only thing that will ever call this. |
| **Measured**              | A verification earned through the route now names an `integration_runs` row whose trigger is `VERIFICATION`, asserted by join. Four mutations: dropping the assertion, turning an absence into a reading, dropping the provenance, and making the shape check wave everything through.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Residual**              | The constraint is `NOT VALID`, so rows written before this migration keep all three columns null. That is deliberate — validating would fail the upgrade on any database that has ever verified an action, and backfilling would invent provenance that was never captured. Those rows remain the honest record that their provenance is unknown.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Owner**                 | Engineering.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

### RR-096 — The first page an MSP sees said nothing was wrong about a customer Adericel could not speak to — **CLOSED 29 Oct 2026**

| Field                | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

| **Description**      | Two defects in the same screenful. (1) The MSP portfolio reported `0 CRITICAL FINDINGS · 0 FAILING CONTROLS · 0 UNKNOWN CONTROLS` for an organisation with sixteen in-scope controls and no assessment, because it counted rows in `assurance_states` — so a control nobody had assessed counted as nothing at all. | **Impact**           | **High, and the worst-placed defect found so far.** The portfolio is the first page an evaluating MSP opens and the page they live in afterwards. All zeroes reads as "nothing wrong" — which is the claim a green dashboard makes, only quieter. `attentionRank` fed off the same count, so the customer Adericel could say least about sorted **last**, below customers it could speak to. And the product contradicted itself on two adjacent pages about the same estate.                                                                                            |
| **Why it is sharp**  | The assurance route's own source comment warns about precisely this: "An empty page is read as 'nothing wrong' — the same claim a green dashboard makes, only quieter, and at the exact moment a customer is deciding what this product is." The lesson had been learned one level down and not carried one level up. The reason vocabulary already carried `NOT_YET_ASSESSED`, the interface already rendered it, and `organisations.ts` and `services/resolution.ts` already used it — `assurance.ts` was the odd one out of three routes answering the same question. |
